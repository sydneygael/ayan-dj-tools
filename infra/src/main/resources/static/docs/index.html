Ayan DJ Tools

Agent IA d'enrichissement de tags audio pour DJs. Ayan scanne vos fichiers audio, détecte les tags manquants, et les enrichit automatiquement via Soundcharts, Spotify et un modèle de langage local via Ollama (llama3.1:8b par défaut). Aucune donnée ne quitte votre machine.

API Reference Tester avec Swagger UI OpenAPI JSON
💡

Le serveur tourne sur le port 8000 par défaut. Tous les endpoints sont préfixés /api. La documentation interactive est disponible sur /swagger-ui.

Fonctionnalités

🎵 Scan & Analyse

Lecture des tags ID3v2.4, Vorbis (FLAC/OGG), AIFF, M4A. Détection automatique des champs manquants.

📡 Enrichissement API

Soundcharts (source primaire) + Spotify fallback. Genres, BPM, tonalité, ISRC, label, popularité.

🤖 Agent IA local

LangChain4j 0.36.0 + Ollama (llama3.1:8b par défaut). 6 assistants spécialisés. Mémoire Redis (TTL 24h).

🔍 RAG / Similarité

Vector store Qdrant. Embeddings nomic-embed-text. Recherche cosinus (seuil 0.7).

🎧 Génération de playlists

Loop-mixing, harmonique (Camelot Wheel), thématique (arc narratif RAG). Export M3U8.

🔒 100 % local & privé

Aucune donnée transmise au cloud. Fonctionne hors-ligne (sauf enrichissement API tiers).

Architecture

Architecture hexagonale (Ports & Adapters) + DDD, structurée en 2 modules Gradle pour enforcer la règle de dépendance à la compilation : infra → domain. Le module domain est un pur java-library sans aucune dépendance Spring ou framework.

Démarrage rapide

1 — Lancer les services

docker-compose up -d

2 — Télécharger les modèles Ollama

# Modèle de chat
docker exec -it dj-tagger-ollama ollama pull llama3.1:8b

# Modèle d'embeddings (RAG)
docker exec -it dj-tagger-ollama ollama pull nomic-embed-text

3 — Lancer le backend

./gradlew infra:bootRun

Le serveur démarre sur http://localhost:8000.

4 — Vérifier

# Santé de l'application
curl http://localhost:8000/actuator/health

# Test de la connectivité Spotify
curl http://localhost:8000/api/spotify/check

Tests

# Tous les tests
./gradlew test

# Module domain uniquement (Java pur, rapide)
./gradlew domain:test

# Tests d'intégration infra (Testcontainers : Redis, PostgreSQL, Qdrant)
./gradlew infra:test

Frontend Flutter (optionnel)

cd ayan_dj_tools_flutter
flutter pub get
flutter run -d windows

Modes d'opération

Chaque plan de tagging est créé dans un mode qui détermine le comportement d'exécution.

ModeComportementCas d'usageEndpoint clé
PLAN Review batch — l'agent propose toutes les opérations, l'utilisateur approuve globalement puis exécute Import massif d'une nouvelle bibliothèque POST /api/plan/{id}/execute
MANUAL Fichier par fichier — confirmation explicite à chaque étape. Le tag n'est écrit qu'après confirmation. Curation fine d'une sélection de tracks POST /api/plan/{id}/operations/{i}/confirm
APPLY Automatique — toutes les opérations s'exécutent en arrière-plan sans intervention. HTTP 202 immédiat. Enrichissement non-critique en batch POST /api/plan/{id}/auto-execute

Agent IA — /api/agent

Agent conversationnel propulsé par LangChain4j 0.36.0 + Ollama (llama3.1:8b par défaut, configurable). L'architecture utilise 6 assistants spécialisés : un classificateur d'intention rapide route chaque message vers l'assistant approprié (FICHIERS · PLANIFICATION · RECHERCHE · PLAYLIST · DECOUVERTE · GENERAL), chacun avec son jeu de tools. La mémoire est gérée via MessageWindowChatMemory stocké dans Redis (TTL 24h, fenêtre 20 messages).

MéthodeCheminDescription
POST /api/agent/chat Chat synchrone — réponse complète + liste des @Tool calls déclenchés
POST /api/agent/chat/stream Chat SSE (text/event-stream) — fragments en temps réel
GET /api/agent/conversations/{id}/history Historique Redis d'une conversation (user + assistant)
DELETE /api/agent/conversations/{id} Effacer l'historique d'une conversation

Flux d'un appel avec tool calls

sequenceDiagram
    actor U as Utilisateur
    participant API as REST API
    participant A as Agent LangChain4j
    participant T as @Tool Functions
    participant SC as Soundcharts
    participant Q as Qdrant
    participant R as Redis

    U->>API: POST /api/agent/chat
    API->>R: charger historique (conversationId)
    API->>A: chatWithToolCalls(message, history)

    A->>T: enrichWithSpotify("Daft Punk", "Around the World")
    T->>SC: GET /song/search/{term}
    SC-->>T: metadata (BPM, key, genres, ISRC…)
    T->>Q: storeVector(track embedding)
    T-->>A: EnrichedTrackMetadata

    A->>T: createPlanForFiles(["/music/track.mp3"])
    T-->>A: TaggingPlan { id, operations[] }

    A-->>API: reply + toolCalls[]
    API->>R: sauvegarder historique (TTL 24h)
    API-->>U: ChatResponse { reply, conversationId, toolCalls }

ℹ️

Le conversationId (UUID) est généré côté serveur si absent de la requête. Le retourner dans chaque requête suivante maintient le contexte de la conversation. Chaque conversation expire après 24h d'inactivité.

Plans de tagging — /api/plan

Un TaggingPlan regroupe N TagOperation (une par fichier audio). Chaque opération suit un cycle de statut.

Cycle de vie d'une opération

stateDiagram-v2
    direction LR
    [*] --> PENDING : opération créée
    PENDING --> APPROVED : approvePlan\nou confirm approved=true
    PENDING --> REJECTED : confirm approved=false\n(mode MANUAL)
    APPROVED --> APPLIED : écriture fichier OK\n(backup → write → commit)
    APPROVED --> ERROR : erreur I/O\n→ rollback automatique
    APPLIED --> [*]
    REJECTED --> [*]
    ERROR --> [*]

Cycle de vie d'un plan (mode PLAN)

sequenceDiagram
    actor U as Client
    participant API as POST /api/plan/create
    participant SVC as PlanManagementService
    participant SC as Soundcharts API
    participant REDIS as Redis

    U->>API: { filePaths, mode: PLAN }
    API->>SVC: createPlan(filePaths)
    loop pour chaque fichier
        SVC->>SC: enrich(artist, title)
        SC-->>SVC: EnrichedTrackMetadata
    end
    SVC->>REDIS: save TaggingPlan (TTL 48h)
    SVC-->>U: TaggingPlan { status: CREATED }

    U->>API: PUT /{id}/approve
    API-->>U: TaggingPlan { status: READY_FOR_REVIEW }

    U->>API: POST /{id}/execute
    loop pour chaque opération APPROVED
        Note over API: backup → writeTags → commit
    end
    API-->>U: BatchApplyResult { applied, errors, durationMs }
MéthodeCheminDescription
POST/api/plan/createCréer un plan (scan + enrich + build)
GET/api/plan/{id}Récupérer un plan
GET/api/plan/{id}/progressCompteurs par statut (PENDING / APPROVED / APPLIED…)
PUT/api/plan/{id}/approveApprouver toutes les opérations PENDING
POST/api/plan/{id}/executeExécuter le plan (mode PLAN)
GET/api/plan/{id}/previewDiff avant/après — lecture seule
GET/api/plan/{id}/historyHistorique d'exécution
DELETE/api/plan/{id}Supprimer le plan de Redis
GET/api/plan/{id}/currentOpération courante (mode MANUAL)
POST/api/plan/{id}/operations/{i}/confirm?approved=trueConfirmer/rejeter (mode MANUAL)
POST/api/plan/{id}/auto-executeLancer en async — HTTP 202 (mode APPLY)
⚠️

Les plans sont stockés dans Redis avec un TTL de 48h. Passé ce délai, l'identifiant retourne HTTP 404.

Tags directs — /api/tags

Écriture de tags sur un fichier sans créer de plan. Backup automatique avant chaque écriture, rollback automatique en cas d'erreur.

MéthodeCheminDescription

Flux d'enrichissement d'un fichier

flowchart TD
    START([🎵 Fichier audio]) --> READ["Lire tags ID3 / Vorbis\nJAudioTaggerAdapter"]
    READ --> MISSING{"Tags\nmanquants ?"}
    MISSING -->|Non| DONE(["✅ Tags complets"])
    MISSING -->|Oui| INFER["Déduire artiste + titre\ndepuis le nom de fichier\n'Artiste - Titre.ext'"]
    INFER --> SEARCH["Soundcharts API\nGET /song/search/{term}"]
    SEARCH -->|Trouvé| META["EnrichedTrackMetadata\ngenres · BPM · tonalité\nISRC · label · popularité"]
    SEARCH -->|Introuvable| SPOTIFY["Spotify fallback\naudio-features + search"]
    SPOTIFY --> META
    SEARCH -->|Erreur| ERR(["❌ NOT_FOUND / ERROR"])
    META --> CACHE["Cache PostgreSQL\nenriched_track_metadata"]
    META --> VEC["Qdrant vector store\nauto-vectorisation"]
    META --> PLAN["TaggingPlan\nopérations prêtes"]
🔒

Sécurité — Les chemins contenant .. sont rejetés (HTTP 400). Seuls les fichiers explicitement fournis par le client sont traités. Aucun scan récursif autonome côté serveur.

Playlists — /api/playlist

Génération intelligente de playlists depuis la bibliothèque vectorisée.

MéthodeCheminAlgorithme
POST /api/playlist/generate Loop-mixing — technique 3/4, paliers de BPM progressifs
POST /api/playlist/generate-harmonic Camelot Wheel — transitions entre tonalités adjacentes compatibles
POST /api/playlist/generate-thematic Thème textuel libre → RAG → arc narratif 5 phases (intro · montée · peak · descente · outro)
POST /api/playlist/export-m3u Export M3U8 téléchargeable (#EXTM3U + #EXTINF)

Algorithmes de génération

    LIB --> FILTER2

Recherche sémantique — /api/rag

Interrogation du vector store Qdrant via embeddings nomic-embed-text (Ollama, 768 dimensions). Similarité cosinus, seuil configurable (défaut 0.7).

MéthodeCheminDescription
GET /api/rag/similar?query=…&limit=5 N tracks les plus similaires à la requête libre, triées par score décroissant 
GET /api/rag/similar?query=dark+techno+135bpm+minor+energetic&limit=10
ℹ️

Les tracks sont vectorisées automatiquement lors de l'enrichissement Soundcharts (enrichWithSpotify @Tool). La collection Qdrant doit contenir au moins quelques entrées pour retourner des résultats.

Stack IA

Tout le traitement IA s'exécute localement via Ollama. Aucune donnée (fichiers, tags, chemins) n'est transmise à un service cloud.

ComposantModèleRôle
Agent conversationnelLangChain4j 0.36.0 + Ollama (llama3.1:8b)6 assistants spécialisés, classification d'intention, orchestration tools
Embeddings RAGnomic-embed-text (Ollama)Vectorisation des tracks pour Qdrant (768 dim)
Vector StoreQdrantRecherche sémantique, Camelot Wheel, similarité
Enrichissement primaireSoundcharts APIGenres, BPM, tonalité, ISRC, label, popularité officielle
Enrichissement secondaireSpotify APIAudio features (si Extended Quota Mode actif)

Changer de modèle Ollama

# Télécharger un autre modèle
docker exec -it dj-tagger-ollama ollama pull llama3.2

# Via variable d'environnement
OLLAMA_CHAT_MODEL=llama3.2 ./gradlew infra:bootRun
💡

Streaming SSE — L'endpoint /api/agent/chat/stream retourne des événements JSON : {"type":"thinking"} (heartbeat) · {"type":"chunk","token":"..."} (fragments, generalAssistant uniquement) · {"type":"done","reply":"...","intent":"FICHIERS"} · {"type":"error"}. Les assistants avec tools utilisent un virtual thread synchrone avec heartbeats — OllamaStreamingChatModel ne supporte pas les tools en LangChain4j 0.36.

Sécurité

AspectDétail
Accès fichiers Seuls les chemins fournis explicitement par le client sont traités. Les chemins contenant .. sont rejetés (HTTP 400). Aucun scan récursif autonome.
CORS Toutes origines autorisées (*), allowCredentials: false. Application desktop uniquement — pas d'exposition publique prévue.
Credentials API Injectés via variables d'environnement ou PUT /api/settings/keys. Jamais retournés en clair dans les réponses API.
Auth HTTP Aucune — l'application tourne en local uniquement. Aucun token requis pour les endpoints REST.
Données personnelles Chemins de fichiers et tags traités 100 % localement. Seuls les requêtes vers Soundcharts/Spotify transmettent artiste + titre.
